# REST API middleware

Базовый адрес локального стенда: `http://127.0.0.1:8000`. Автоматическая OpenAPI-документация доступна по `/docs`, схема — по `/openapi.json`.

Защищённые маршруты принимают JWT в заголовке `X-Auth-Token` или `Authorization: Bearer <JWT>`. Публичны страницы веб-интерфейса, статика, `/api`, `/health` и `/auth/login`. Для входящих интеграций действуют отдельные правила, приведённые ниже.

```http
X-Auth-Token: <JWT>
```

## Границы действий и задач

Все ответы LLM (включая локальные правила) проходят проверку `action` по серверной матрице прав. Неизвестное, запрещённое действие или некорректная верхняя структура ответа заменяются на `access_denied`; исходные текст и данные отбрасываются. Это не полноценная валидация всех реквизитов документов 1С и не гарантия достоверности свободной консультации.

Веб-клиент при сетевой ошибке или неуспешном HTTP-ответе не подставляет успешный финансовый результат: показывает сообщение о невыполненном запросе. Монитор помечает `is_mock_data=true` как демонстрационные данные.

Для канбана единая область видимости применяется к списку, доске, карточке по ID, статистике, уведомлениям и CSV:

- `admin`, `director`, `cfo`: все задачи;
- `manager`, `warehouse`: свои задачи и задачи своего подразделения; отсутствие подразделения не даёт общих прав;
- `employee`, `service_bridge`: задачи, где пользователь — автор или исполнитель;
- неизвестная роль: пустая область видимости.

Изменение и перемещение требуют видимости задачи. Сотрудник и сервисная учётная запись не могут назначать другого исполнителя; перенос в чужое подразделение доступен только руководству и администратору. Удалять может администратор или автор. Повторная инициализация демо-данных не восстанавливает отозванные роли существующих пользователей.

Проверка ИНН принимает ASCII-цифры, проверяет длину и контрольные разряды, отклоняет полностью нулевой номер. Она не подтверждает регистрацию контрагента в ФНС. Ставки в учебных калькуляторах не являются автоматически актуальными нормативными данными.

## Системные маршруты

| Метод | Путь | Назначение | Доступ |
|---|---|---|---|
| GET | `/` | веб-интерфейс | публичный |
| GET | `/api` | краткий статус сервиса | публичный |
| GET | `/health` | состояние БД и конфигурации LLM | публичный |

`/health` возвращает `status`, `service`, `db` и `llm`.

## Авторизация и пользователи

| Метод | Путь | Назначение | Доступ |
|---|---|---|---|
| POST | `/auth/login` | получить JWT | публичный, 60 запросов/мин при включённом лимитере |
| POST | `/auth/register` | создать пользователя | admin |
| GET | `/auth/me` | получить свой профиль | любой пользователь |
| PUT | `/auth/me` | изменить свой профиль | любой; роль меняет только admin |
| GET | `/auth/users` | список пользователей | любой, область зависит от роли |
| PUT | `/auth/users/{user_id}` | изменить пользователя | admin |
| DELETE | `/auth/users/{user_id}` | удалить пользователя | admin |

Пример входа:

```json
{
  "username": "admin",
  "password": "admin"
}
```

Ответ содержит `access_token`, `token_type` и объект `user`. Учётные данные из примера создаются только как демонстрационные и должны быть заменены вне локального стенда.

`GET /auth/users` поддерживает `department_id`, `skip`, `limit`. Для сотрудника и менеджера область списка принудительно ограничивается их подразделением; администратор может выбрать подразделение явно.

## Подразделения

| Метод | Путь | Назначение | Доступ |
|---|---|---|---|
| GET | `/departments` | список подразделений | любой пользователь |
| POST | `/departments` | создать подразделение | admin |
| PUT | `/departments/{dept_id}` | изменить подразделение | admin |
| DELETE | `/departments/{dept_id}` | удалить подразделение | admin |

При удалении подразделения ссылки пользователей на него обнуляются.

## Чат и метаданные

| Метод | Путь | Назначение | Доступ |
|---|---|---|---|
| POST | `/chat` | получить ответ LLM и формализованное действие | любой пользователь, 200 запросов/мин при включённом лимитере |
| POST | `/update_metadata` | заменить индекс метаданных | admin |

Запрос чата:

```json
{
  "messages": [
    {"role": "user", "text": "Покажи должников"}
  ],
  "context": "Раздел: Продажи"
}
```

Ответ:

```json
{
  "role": "assistant",
  "text": "Формирую список дебиторов...",
  "action": "get_debtors",
  "data": {}
}
```

Допустимые действия перечислены в `docs/ARCHITECTURE.md`. Если `action=create_kanban_task`, middleware создаёт задачу и добавляет её идентификатор в `data.task_id`.

Запрос обновления метаданных:

```json
{
  "items": [
    {
      "name": "Справочник.Контрагенты",
      "synonym": "Контрагенты",
      "fields": [
        {"name": "Наименование", "synonym": "Наименование", "type": "Строка"}
      ]
    }
  ]
}
```

## Канбан

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/kanban/board` | задачи и конфигурация четырёх колонок |
| GET | `/kanban/tasks` | список задач с фильтрами и пагинацией |
| POST | `/kanban/tasks` | создать задачу |
| GET | `/kanban/tasks/export` | выгрузить видимые задачи в CSV |
| GET | `/kanban/tasks/{task_id}` | получить задачу |
| PUT | `/kanban/tasks/{task_id}` | изменить задачу |
| POST | `/kanban/tasks/move` | переместить задачу |
| DELETE | `/kanban/tasks/{task_id}` | удалить задачу |
| GET | `/kanban/stats` | агрегированная статистика |
| GET | `/kanban/notifications` | последние задачи для уведомлений |
| GET | `/kanban/sync/1c` | получить ещё не синхронизированные задачи |
| POST | `/kanban/sync/1c` | пометить задачи синхронизированными |

Все маршруты канбана требуют JWT; маршруты `/kanban/sync/1c` требуют роль `admin`.

Поля создания задачи:

```json
{
  "title": "Подготовить отчёт",
  "description": "Продажи за август",
  "column": "todo",
  "priority": "high",
  "assignee": "ivanov",
  "due_date": "2026-09-05",
  "tags": ["отчёт", "продажи"],
  "source": "1c",
  "department_id": 1
}
```

Допустимые колонки: `todo`, `in_progress`, `review`, `done`. Приоритеты: `low`, `medium`, `high`, `urgent`. Источники: `web`, `chat`, `1c`, `1c_kanban`, `1c_mobile`.

`GET /kanban/tasks` поддерживает `filter_dept`, `filter_assignee`, `filter_priority`, `skip`, `limit`. Фильтр подразделения применяется только для администратора.

Перемещение:

```json
{
  "task_id": 42,
  "column": "in_progress",
  "position": 0
}
```

Подтверждение синхронизации с 1С принимает JSON-массив идентификаторов:

```json
[41, 42, 43]
```

## Голос, QR и входящие интеграции

| Метод | Путь | Фактическое правило доступа |
|---|---|---|
| POST | `/voice/transcribe` | JWT активного пользователя |
| GET, POST | `/qr/generate` | JWT активного пользователя |
| POST | `/integrations/email/incoming` | JWT активного пользователя либо верный `X-Email-Hook-Secret`, если задан `EMAIL_HOOK_SECRET` |
| POST | `/integrations/telegram/webhook` | обязательны настройка `TELEGRAM_WEBHOOK_SECRET` и совпадающий заголовок `X-Telegram-Bot-Api-Secret-Token` |
| POST | `/integrations/vk/callback` | обязательны настройка `VK_SECRET_KEY` и совпадающее строковое поле `secret` |
| POST | `/integrations/telegram/simulate`, `/integrations/vk/simulate` | JWT; admin, director, cfo или manager |

Для email без JWT и без настроенного секрета возвращается `401`; при настроенном секрете и неверном заголовке без JWT — `403`. Вебхуки Telegram/VK без настроенного секрета возвращают `503`, с неверным секретом — `403`; обработчик сообщения при этом не вызывается. Это не меняет протокол long polling.

Симуляторы перехватывают отправку сообщений, но могут вызывать настроенный LLM. Они не являются полностью изолированным тестовым окружением.

В `/chat` сервисный JWT `service_bridge` получает роль `employee`; заголовки `X-1C-User-Name`, `X-1C-User-Role` и поля `user_identity`, `user_role` не удостоверяют другого пользователя и не повышают права. Для финансовых запросов нужен личный JWT пользователя с соответствующей ролью. Задачи сервисного моста записываются от имени сервисной учётной записи. Формат запросов BSL сохранён, но прежняя передача полномочий по заголовку прекращена; живой сценарий личного входа в клиенте 1С требует отдельной проверки.

Отправители реальных мессенджеров и почты без подтверждённой привязки учётной записи получают роль `employee`, даже если в отображаемом имени есть «директор» или оно совпадает с логином администратора. Секрет вебхука удостоверяет канал доставки, но не роль сотрудника. В авторизованных симуляторах используется роль владельца JWT.

## Ошибки

Для `/business/debt/calculate-penalty` поле `custom_key_rate` задаёт конечную неотрицательную ставку в процентах **годовых**. Дневная ставка не поддерживается этим полем. Расчёт разбивается по календарным годам с делителями 365/366 и округлением суммы каждого периода до копеек. Проверка арифметики не подтверждает нормативную актуальность встроенной таблицы ставок.

- `400` — некорректная прикладная операция, например занятый логин;
- `401` — токен отсутствует, недействителен или истёк;
- `403` — роль или область видимости не разрешает действие;
- `404` — пользователь, подразделение или задача не найдены;
- `422` — тело запроса не соответствует Pydantic-модели;
- `429` — превышен лимит запросов;
- `500` — внутренняя ошибка LLM, индекса или хранилища; обработчики чата, обновления метаданных и записи задач возвращают нейтральный `Internal server error`, без текста исключения.
- `503` — входящий вебхук Telegram/VK не настроен.
