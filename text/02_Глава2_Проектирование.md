2 ПРОЕКТИРОВАНИЕ ИНТЕЛЛЕКТУАЛЬНОГО АССИСТЕНТА ДЛЯ 1С:УНФ

2.1 Проектирование архитектуры системы

Проектируемая система построена по двухзвенной клиент-серверной схеме и состоит из:
1. Клиентская часть (расширение 1С:УНФ) — предоставляет чат-интерфейс, обрабатывает быстрые команды, выгружает метаданные и безопасно исполняет полученные от middleware инструкции (белый список действий).
2. Серверная часть (Python middleware на FastAPI) — предоставляет HTTP API для авторизации, канбан-доски, семантического поиска и взаимодействия с внешним LLM-провайдером.

Вынос тяжелых операций (векторизация, запросы к нейросети) в middleware позволяет обойти ограничения платформы 1С на работу с Python-библиотеками машинного обучения и легко менять LLM-модели без изменения кода в 1С. Архитектура решения и связи компонентов представлены на рисунке 2.1.

Рисунок 2.1 — Архитектура решения: компоненты и взаимосвязи

Внутренняя структура расширения 1С включает: модуль гибридного интерфейса (HTML-поле + таблица истории), модуль сетевой интеграции (JSON-обмен по HTTP) и модуль диспетчера команд (whitelist-исполнение). Middleware разделено на FastAPI API-слой, сервисы авторизации (`auth_service`), канбан-задач (`kanban_service`), метаданных (`metadata_service`) и интеграции с LLM (`llm_service`).

2.2 Проектирование алгоритмов и сценариев работы

Алгоритм обработки запроса пользователя включает шаги:
1. Ввод сообщения в чат-форме 1С.
2. Отправка JSON-запроса (массив сообщений диалога + контекст формы) в middleware по HTTP.
3. Семантический поиск по векторному индексу метаданных базы 1С для подбора top-K подходящих объектов (RAG).
4. Формирование системного промпта (`system prompt`), включающего роль ассистента, whitelist-команды, few-shot примеры и метаданные-кандидаты.
5. Запрос к LLM и получение структурированного JSON-ответа (поля `text`, `action`, `data`).
6. Многоуровневый разбор (парсер JSON с постобработкой намерения) и возврат результата в 1С.
7. Отображение ответа ассистента в чате и запуск диспетчера команд в 1С при наличии `action`.

Последовательность вызовов при обработке запроса приведена на рисунке 2.2.

Рисунок 2.2 — Диаграмма последовательностей «Отправка сообщения»

Системный промпт строится из пяти блоков:
1. Роль: «Ты — ИИ-ассистент для 1С:УНФ, помогаешь пользователям...»
2. Разделение намерений: различие вопросов по методологии (`expert_answer`) и команд выполнения действий.
3. Белый список действий: `open_list`, `open_form`, `find_object`, `create_object`, `get_status`, `get_stock`, `get_debtors`, `run_analytics`, `create_kanban_task`, `show_kanban`.
4. Few-shot примеры (пары запрос-ответ):
   - «Открой заказы» → `{"text": "Открываю...", "action": "open_list", "data": {"type": "Документ.ЗаказПокупателя"}}`
   - «Проверен ли заказ 32?» → `{"text": "Ищу...", "action": "find_object", "data": {"type": "Документ.ЗаказПокупателя", "number": "32"}}`
   - «Добавь задачу: подготовить отчет до пятницы» → `{"text": "Создаю...", "action": "create_kanban_task", "data": {"title": "Подготовить отчет", "due_date": "2026-04-24", "priority": "medium"}}`
5. Контекст метаданных: top-7 семантически близких объектов.

Алгоритм безопасного создания объектов `create_object` основан на пошаговой проверке контрагента (Шаг 1) и номенклатуры (Шаг 2). При отсутствии элемента ассистент предлагает создать его в 1С по предзаполненным реквизитам, и только после подтверждения открывает форму нового документа (Шаг 3).

2.3 Проектирование структуры данных и «базы знаний» ассистента

База знаний ассистента формируется путем выгрузки метаданных 1С (Имя, Синоним, Реквизиты) в JSON-файл `metadata_store.json`. Для каждого объекта строится текстовое описание (Синоним + Имя + Реквизиты с типами), которое векторизуется моделью `paraphrase-multilingual-MiniLM-L12-v2`. Схема поиска представлена на рисунке 2.3.

2.5 Проектирование пользовательского интерфейса

Интерфейс ассистента в 1С спроектирован по гибридной схеме: диалог отображается через HTML-поле (с визуализацией бабблов сообщений, градиентным фоном и анимацией ввода), а история хранится в реквизите управляемой формы `ЧатИстория` (ТаблицаЗначений). 2.6 Проектирование системы авторизации и ролевой модели

Безопасность доступа обеспечивается с помощью токенов JWT, передаваемых в заголовке `X-Auth-Token`.
Ролевая модель разграничивает права:
- `admin` — видит и управляет всеми задачами и пользователями, имеет доступ к полной аналитике;
- `manager` — управляет задачами сотрудников своего департамента, работает с документами и аналитикой;
- `employee` — видит и перемещает только свои задачи, пользуется консультационным чатом.

Пример полезной нагрузки (payload) JWT:
```json
{
  "sub": "username_here",
  "user_id": 12,
  "role": "manager",
  "department_id": 3,
  "exp": 1717200000
}
```
Схема JWT-авторизации представлена на рисунке 2.6. При получении ошибки 401 расширение 1С запускает авторетрай: сбрасывает токен, запрашивает новый на эндпоинте `/auth/login` с сервисными учетными данными и повторяет исходный запрос.

2.7 Проектирование мобильного клиента

Для обеспечения совместимости с мобильным клиентом 1С учитываются ограничения мобильного рендеринга (отсутствие CSS-анимаций, лимиты JS). Реализовано разделение форм:
- На десктопе форма чата и доска канбан используют HTML-поля с интерактивными стилями и JS-обработчиками кликов.
- В мобильном клиенте для доски канбан используется нативная форма с управляемой таблицей значений `ЗадачиТаблица`. Просроченные задачи подсвечиваются условным оформлением (красный цвет), а клик по строке открывает мобильное контекстное меню выбора колонок.

Выбор формы происходит динамически в функции `ЭтоМобильныйКлиент()` на основе результата работы `ПолучитьИнформациюОСистемеКлиента()`.
