2 ПРОЕКТИРОВАНИЕ ИНТЕЛЛЕКТУАЛЬНОГО АССИСТЕНТА ДЛЯ 1С:УНФ

2.1 Проектирование архитектуры системы

Проектируемая система состоит из двух основных частей:
1) клиентская часть — расширение конфигурации 1С:УНФ, включающее форму чата, обработчики событий интерфейса и исполнители команд;
2) серверная часть — middleware на Python, предоставляющая HTTP API для чата, авторизации, управления канбан‑задачами и обновления метаданных, выполняющая семантический поиск и обращение к LLM.

Причины выбора двухзвенной архитектуры:
- ограничения платформы 1С по работе с внешними LLM и библиотеками машинного обучения;
- необходимость вынести сетевое взаимодействие и тяжелые вычисления (эмбеддинги) из 1С;
- повышение расширяемости: смена LLM‑провайдера или моделей производится в middleware без переписывания расширения.

Компоненты архитектуры:
- **1С‑расширение**:
  - форма обработки «Чат с ассистентом» с гибридным интерфейсом: HTML‑поле для рендера диалога с CSS‑оформлением и табличный реквизит `ЧатИстория` для хранения сообщений;
  - функции серверной генерации HTML‑чата (`СгенерироватьЧатHTML`, `СгенерироватьЧатHTMLЗагрузка`) с аватарами, бабл‑схемой, анимированным индикатором печати и автопрокруткой к последнему сообщению;
  - быстрые кнопки как стандартные элементы формы (Заказы, Канбан, Сегодня, Должники, Клиенты);
  - модуль отправки запросов в middleware;
  - модуль выполнения команд (навигация, поиск, подготовка документов, аналитика, канбан);
  - модуль выгрузки метаданных (список объектов конфигурации и их реквизиты).
- **Python middleware**:
  - FastAPI‑приложение (эндпоинты `/chat`, `/auth/login`, `/auth/me`, `/auth/register`, `/auth/users`, `/departments`, `/kanban/tasks`, `/kanban/board`, `/kanban/stats`, `/kanban/notifications`, `/kanban/tasks/export`, `/kanban/sync/1c`, `/update_metadata`);
  - сервис авторизации (auth_service) — JWT‑токены, хеширование паролей (bcrypt), хранение пользователей и департаментов в SQLite, ролевая модель (admin/manager/employee);
  - сервис канбан‑задач (kanban_service) — CRUD задач, фильтрация по ролям, статистика, CSV‑экспорт, отслеживание просроченных задач;
  - сервис LLM (llm_service) — формирование system prompt, запрос к модели, разбор ответа, пост‑обработка намерений;
  - сервис метаданных (metadata_service) — хранение индекса, построение векторного пространства, поиск топ‑к кандидатов;
- **LLM‑провайдер**:
  - сервис, предоставляющий совместимый API для чат‑комплишенов;
  - модель, способная работать с русским языком и выдавать структурированные ответы.

Архитектура решения построена по принципу двухзвенной клиент-серверной системы с чётким разделением ответственности между компонентами. Клиентская часть — это расширение конфигурации 1С:УНФ, содержащее форму чата с таблицей истории сообщений, HTML-полем для канбан-доски и кнопками быстрых команд. Серверная часть — middleware на Python (FastAPI), выполняющий семантический поиск по метаданным, формирование промптов и обращение к LLM-провайдеру. Хранилище состоит из трёх элементов: предвычисленных эмбеддингов метаданных (файл .npy), JSON-индекса объектов конфигурации и базы данных SQLite, где хранятся пользователи, департаменты и канбан-задачи. Такое разделение позволяет менять LLM-провайдера или добавлять новые команды без модификации кода 1С.

Рисунок 2.1 — Архитектура решения: компоненты и взаимосвязи

Диаграмма демонстрирует, что все действия, изменяющие данные в 1С, выполняются исключительно на стороне клиента по заранее определённому белому списку команд, что исключает возможность несанкционированных операций со стороны внешней модели.

Основной принцип безопасности архитектуры — **строгое разделение ответственности**:
- LLM отвечает за интерпретацию запроса и выбор действия из ограниченного набора;
- 1С исполняет только заранее запрограммированные действия и не выполняет произвольный код по просьбе модели;
- обмен ведется в формате JSON по фиксированной схеме;
- доступ к API middleware требует JWT‑токен, роль пользователя проверяется на каждом запросе;
- канбан‑задачи фильтруются по роли: администратор видит все задачи, менеджер — задачи своего департамента, сотрудник — только свои.

Внутренняя декомпозиция модулей расширения 1С:
- модуль интерфейса (инициализация табличного хранилища ЧатИстория, генерация HTML‑чата с CSS‑оформлением, быстрые кнопки, обработчики открытия отдельной формы канбан‑доски);
- модуль интеграции (сериализация запроса в JSON, HTTP‑вызов middleware, разбор ответа, авторетрай при 401);
- модуль исполнения команд (ветвление по `action`, открытие форм, поиск, выполнение запросов к данным, создание канбан‑задач, отображение доски);
- модуль обновления метаданных (обход метаданных конфигурации, формирование списка объектов и реквизитов, отправка в middleware).

Внутренняя декомпозиция middleware:
- слой API (FastAPI endpoints) — принимает/отдает JSON, проверяет JWT‑токен, отвечает за коды ошибок;
- слой авторизации (auth_service) — регистрация/логин пользователей, выдача JWT, хранение в SQLite, ролевая модель;
- слой канбан (kanban_service) — CRUD задач, фильтрация, статистика, экспорт, отслеживание просрочки;
- слой «знаний» (metadata_service) — хранит и индексирует метаданные, выполняет семантический поиск;
- слой LLM (llm_service) — формирует prompt, запрашивает модель, извлекает JSON‑ответ, пост‑обработка намерений.

2.2 Проектирование алгоритмов и сценариев работы

Алгоритм обработки пользовательского запроса включает следующие этапы:
1) пользователь вводит сообщение в чат‑форме 1С;
2) расширение формирует JSON‑запрос (messages + context) и отправляет его в middleware по HTTP;
3) middleware выполняет семантический поиск по индексу метаданных, чтобы сформировать список кандидатов (доступных объектов 1С, близких к запросу);
4) middleware собирает system prompt, который:
   - описывает роль ассистента;
   - задает правила определения намерения (консультация vs выполнение);
   - перечисляет допустимые действия (actions) и формат ответа;
   - добавляет текущий контекст (например, имя формы в 1С);
   - добавляет найденных кандидатов (объекты и часть реквизитов);
5) middleware обращается к LLM и получает текст ответа;
6) middleware извлекает JSON (многоуровневый разбор) и возвращает ответ в 1С;
Многоуровневый разбор JSON включает: (1) извлечение из markdown‑блока ```json ... ```; (2) поиск всех корректных объектов `{ ... }` в тексте; (3) предобработку кандидата (удаление комментариев, trailing‑запятых, замена одинарных кавычек); (4) попытку с заменой двойных скобок (артефакт f‑строк); (5) при невозможности разобрать JSON — очистку текста от артефактов JSON и возврат как expert_answer. Таким образом обеспечивается устойчивость к «неидеальным» ответам LLM.
7) 1С отображает `text` в чате;
8) если `action` задан — вызывается исполнитель команды в 1С, который открывает форму/ищет объект/готовит документ и т. п.

Диаграмма последовательностей иллюстрирует полный цикл обработки одного пользовательского запроса. После ввода сообщения в форму чата 1С-клиент читает до 20 последних строк из табличного реквизита ЧатИстория, преобразует роль "bot" в "assistant" и формирует JSON-массив messages. Запрос POST /chat передаёт этот массив вместе с контекстом текущей формы. Middleware выполняет RAG-поиск: запрос пользователя векторизуется через предвычисленные эмбеддинги, выбираются top-7 семантически близких объектов конфигурации с их реквизитами и типами. Эти кандидаты вместе с правилами определения намерений и few-shot примерами подаются в system prompt модели GLM-5.1. Модель возвращает JSON с полями text, action и data. Middleware проверяет action по белому списку, при необходимости применяет пост-обработку (например, корректировка expert_answer → show_kanban) и возвращает ответ в 1С. Если action не пустой, 1С вызывает диспетчер команд ВыполнитьКомандуАссистента(), который открывает формы, создаёт объекты или запрашивает данные.

Проектирование протокола команд (action)

Для управления действиями выбран подход «команда‑как‑данные»: LLM возвращает строго определенный JSON‑объект:
{
  "text": "...",
  "action": "open_list | open_form | create_object | ...",
  "data": { ... }
}

Список разрешенных действий фиксируется в middleware и в 1С и является «белым списком»:
- `open_list` — открыть список объекта;
- `open_form` — открыть форму объекта/отчета;
- `find_object` — найти объект по номеру;
- `create_object` — подготовить создание объекта;
- `prepare_payment`, `accrual_writeoff` — финансовые операции (подготовка документа);
- `warehouse_move` — подготовка перемещения;
- `employee_info` — карточка сотрудника;
- `get_dossier` — сбор досье по контрагенту/номенклатуре;
- `get_status` — получение статуса документа;
- `get_stock` — получение остатков;
- `get_debtors` — список должников;
- `run_analytics` — упрощенная аналитика;
- `create_kanban_task` — создание задачи на канбан‑доске;
- `show_kanban` — отображение канбан‑доски со всеми задачами.
Для компенсации случаев, когда LLM неверно определяет намерение, реализована пост‑обработка: если модель вернула `expert_answer`, но запрос содержит ключевые слова «канбан/доска/задачи» + «покажи/открой», действие автоматически корректируется на `show_kanban`; аналогично, при наличии слов «создай задачу/добавь задачу» действие меняется на `create_kanban_task`. Также при получении неизвестного действия (не из белого списка) система автоматически откатывается к `expert_answer`.

Для каждого действия задается ожидаемая структура `data`. Примеры:
- `find_object`: { "type": "Документ.ЗаказПокупателя", "number": "32" }
- `get_stock`: { "fields": { "Item": "Ноутбук" } }
- `create_object`: { "type": "Документ.ЗаказПокупателя", "fields": { "Client": "ООО Ромашка", "Item": "Цемент", "Quantity": 10 } }
- `create_kanban_task`: { "title": "Подготовить отчёт", "column": "todo", "priority": "high", "assignee": "Иванов", "due_date": "2026-04-30" }
- `show_kanban`: { }

Выбор строгих структур данных уменьшает неоднозначность, упрощает тестирование и позволяет расширять систему без изменения базового протокола.

Алгоритм безопасного создания объектов (цепочка шагов)

Чтобы снизить вероятность ошибок при автоматизации, в расширении реализуется сценарий подготовки создания с пошаговыми проверками:
1) подготовка структуры значений заполнения на сервере 1С (по реквизитам, полученным от LLM);
2) проверка существования контрагента:
   - если контрагент не найден — спросить пользователя о создании;
   - при подтверждении открыть форму создания контрагента с предзаполненными данными;
3) проверка существования номенклатуры:
   - аналогично предложить создание товара/услуги;
4) финальный шаг — открыть форму нового документа/карточки с заполненными реквизитами.

Выбор подхода «цепочка ответственности» позволяет расширять сценарий (например, добавить проверку склада, банковского счета, статьи ДДС) без изменения логики диалога.

2.3 Проектирование структуры данных и «базы знаний» ассистента

Ключевой задачей ассистента является ориентация в конкретной базе 1С:УНФ. Для этого вводится слой «знаний о метаданных», включающий:
- полные имена объектов (например, `Документ.ЗаказПокупателя`, `Отчет.Продажи`);
- человеко‑понятные синонимы (например, «Заказ покупателя», «Продажи»);
- набор реквизитов объекта (имя, синоним и тип реквизита, например: Строка, Число, СправочникСсылка.Контрагенты).

На стороне 1С:
- метаданные собираются серверной процедурой обхода коллекций «Справочники», «Документы», «Отчеты»;
- для каждого объекта формируется структура: `name`, `synonym`, `fields[]`;
- результирующий пакет `{ items: [...] }` сериализуется в JSON и отправляется в middleware.

На стороне middleware:
- метаданные сохраняются в файл `metadata_store.json`;
- для каждого элемента формируется текст для векторизации: синоним + имя объекта + расширенные синонимы + (часть) реквизитов;
- вычисляются эмбеддинги и создается индекс, поддерживающий поиск ближайших объектов по косинусному сходству.
В текст для векторизации дополнительно включается тип реквизита (если он выгружен из 1С), что позволяет модели различать строковые поля, числовые показатели и ссылки на другие объекты.

Ключевым отличием предлагаемого решения от «чистого» LLM является использование контекста реальных метаданных конфигурации. При нажатии кнопки «Обновить метаданные» расширение 1С обходит коллекции Справочники, Документы и Отчёты, формируя для каждого объекта структуру с полями name (внутреннее имя, например Документ.ЗаказПокупателя), synonym (человеко-читаемый синоним, например «Заказ покупателя») и fields (массив реквизитов, каждый с name, synonym и type). Тип реквизита (например, СправочникСсылка.Контрагенты, Число, Строка) критически важен для LLM, поскольку позволяет модели различать ссылки на другие объекты, строковые наименования и числовые показатели. Эти данные векторизуются с помощью мультиязычной модели paraphrase-multilingual-MiniLM-L12-v2 и сохраняются в файле .npy, а сами метаданные — в JSON. При каждом запросе пользователя middleware вычисляет косинусное сходство между вектором запроса и векторами всех объектов, возвращая top-7 кандидатов с наибольшим значением similarity.

Рисунок 2.3 — Структура элемента метаданных и место в процессе RAG

Схема наглядно показывает, что текст для векторизации формируется из четырёх компонентов: синонима объекта, его внутреннего имени, расширенных доменных синонимов (словарь «контрагент→клиент→покупатель») и первых пяти реквизитов с указанием их типов. Такой состав обеспечивает высокую полноту поиска даже при разнообразии пользовательских формулировок.

Семантический поиск выполняется по классической схеме:
1) запрос пользователя преобразуется в вектор v(q);
2) каждый элемент метаданных представлен вектором v(i);
3) вычисляется косинусное сходство:
   sim(q,i) = (v(q) · v(i)) / (||v(q)|| · ||v(i)||);
4) выбираются top‑K элементов с максимальным значением sim(q,i).

Дополнительно реализован fallback‑алгоритм поиска по пересечению слов (word overlap), который используется при отсутствии ML‑модели (sentence‑transformers). Алгоритм разбивает запрос пользователя и текст элемента метаданных на слова, вычисляет количество совпадающих слов и возвращает элементы с максимальным перекрытием. Это обеспечивает работоспособность системы даже без установки ML‑зависимостей.

Дополнительно в «текст для векторизации» вводятся доменные синонимы (например, «контрагент» ↔ «клиент», «накладная» ↔ «реализация/поступление»). Это позволяет повысить полноту поиска при различиях пользовательских формулировок.

Связи между таблицами:

- `users.department_id` → `departments.id` — связь «многие‑к‑одному»: несколько пользователей могут относиться к одному департаменту;
- `departments.head_user_id` → `users.id` — связь «один‑к‑одному»: департамент имеет одного руководителя;
- `departments.parent_id` → `departments.id` — самоссылка, обеспечивающая иерархическую структуру департаментов (подразделения внутри подразделений).

Для хранения данных авторизации и канбан-задач используется встроенная СУБД SQLite, доступ к которой осуществляется через ORM-библиотеку SQLAlchemy. Декларативные модели описывают три основные таблицы: users (пользователи системы с полями username, password_hash, role, department_id), departments (иерархия департаментов с полями name, head_user_id, parent_id) и kanban_tasks (задачи канбан-доски с полями title, column, priority, assignee, department_id, synced_1c). Связь users → departments многие-к-одному реализована через внешний ключ department_id. Дополнительно таблица departments содержит head_user_id — ссылку на руководителя департамента (один-к-одному с users) и parent_id — рекурсивную ссылку для построения иерархии подразделений. Таблица kanban_tasks через department_id привязана к департаменту, что позволяет менеджерам видеть задачи своего подразделения. SQLAlchemy автоматически создаёт таблицы при первом запуске и обеспечивает переносимость кода между SQLite (прототип) и PostgreSQL (промышленная эксплуатация) без изменений в бизнес-логике.

Представленная схема показывает, что ролевая модель не требует отдельной таблицы ролей: ограничение жёстко задано в поле role (строка admin/manager/employee), а фильтрация данных реализована программно в методах сервисов. Это упрощает прототип, сохраняя при этом возможность расширения до полноценной RBAC-модели в будущем.

Для отображения таблиц на Python‑классы используется ORM‑фреймворк SQLAlchemy: каждый класс наследуется от `declarative_base()`, поля описываются через `Column` с указанием типа и ограничений, а доступ к данным осуществляется через сессии `sessionmaker`. Выбор SQLite в качестве движка базы данных обусловлен следующими факторами: встроенная архитектура (отсутствие необходимости в отдельном сервере БД), хранение всей базы в единственном файле на диске, нулевая конфигурация при развёртывании, а также достаточная функциональность для прототипа системы.

2.5 Проектирование пользовательского интерфейса

Требования к интерфейсу ассистента:
- минимальная «стоимость» взаимодействия (ввод фразы вместо поиска по меню);
- визуальное разделение сообщений пользователя и ассистента;
- сохранение истории диалога в рамках сессии формы;
- наличие быстрых кнопок для популярных действий (открыть заказы, продажи за период, канбан‑доска и т. п.);
- индикатор ожидания ответа, чтобы пользователь понимал состояние системы;
- совместимость с мобильным клиентом «1С:Предприятие».

В прототипе выбран гибридный подход к реализации интерфейса:
- **HTML‑поле** (реквизит «ЧатHTML» типа Строка) — основной элемент для отображения истории сообщений. На каждое обновление чата серверная функция `СгенерироватьЧатHTML()` собирает HTML‑документ с инлайн‑CSS, в котором каждое сообщение оформлено как «бабл» с аватаром, временной меткой и градиентным фоном (оранжевый #FF6B00→#FF8C42 для пользователя, тёмно‑синий #2D2D48 для ассистента). При активном HTTP‑запросе к LLM функция `СгенерироватьЧатHTMLЗагрузка()` добавляет в конец документа анимированный индикатор печати с тремя точками. Финальный фрагмент скрипта выполняет `scrollTop = scrollHeight`, что обеспечивает автопрокрутку к последнему сообщению;
- **табличный реквизит** «ЧатИстория» типа ТаблицаЗначений с колонками Автор, Текст, Время и ТипСообщения — служит хранилищем истории сообщений. При отправке нового запроса процедура `ОтправитьСообщение` читает до 20 последних строк из ЧатИстория, преобразует значение «bot» в роль «assistant» и формирует JSON‑массив `messages` для middleware. Хранение истории в табличной части обеспечивает её сохранность при перезаписи формы и упрощает отправку в middleware;
- **стандартные кнопки формы** — быстрые команды (Заказы, Канбан, Сегодня, Должники, Клиенты) реализованы как кнопки с обработчиками нажатия, что гарантирует работу в мобильном клиенте 1С;
- **отдельная форма канбан‑доски** (`Обработка.КанбанДоска.Форма` для десктопа и `Обработка.КанбанДоска.МобильнаяФорма` для мобильного клиента) — расширение «Канбан‑доска» вынесено в самостоятельный модуль и открывается из формы чата по нажатию кнопки. Автоматический выбор формы по результату вызова `ПолучитьИнформациюОСистемеКлиента()` обеспечивает корректную работу как на ПК, так и на смартфонах и планшетах.

Интерфейс ассистента построен на гибридной схеме «HTML‑поле для отображения и табличное хранилище для данных». При открытии формы серверная процедура `ПриСозданииНаСервере` инициализирует ЧатИстория приветственным сообщением, после чего формирует ЧатHTML вызовом `СгенерироватьЧатHTML()`. Каждое последующее изменение истории — добавление пользовательского сообщения, ответа ассистента или индикатора загрузки — выполняется через серверную процедуру `ДобавитьСообщениеВЧатНаСервере`, которая обновляет табличный реквизит и перегенерирует HTML‑строку. Поле ввода `ТекстСообщения`, кнопка отправки и панель быстрых команд расположены под HTML‑полем; авторизация с middleware происходит автоматически в `ПриОткрытии`, токен сохраняется в реквизите формы и используется во всех последующих запросах через заголовок `X-Auth-Token`.

Рисунок 2.5 — Макет формы чата в 1С

Гибридный подход «HTML‑поле + табличное хранилище» позволяет получить современный визуальный стиль чата (бабл‑схема, аватары, градиенты, анимация индикатора печати) при сохранении совместимости с мобильным клиентом «1С:Предприятие» и устойчивости истории сообщений к перезаписи формы. Канбан‑доска как самостоятельная функциональность вынесена в отдельную форму расширения «Канбан‑доска», что соответствует принципу разделения ответственности и упрощает независимое развитие двух функциональных областей.

Проектирование пользовательских сценариев (пример)

Сценарий S‑01 «Открыть список заказов»:
1) пользователь нажимает быстрый пункт «Заказы» или вводит фразу «Открой список заказов покупателей»;

1) пользователь вводит «Проведен ли заказ 32?»;
2) middleware возвращает `action=get_status`, `data.type=Документ.ЗаказПокупателя`, `data.number=32`;
3) расширение выполняет серверный запрос к данным и возвращает результат в чат.

Сценарий S‑03 «Подготовить заказ покупателя»:
1) пользователь вводит «Создай заказ покупателя для ООО Ромашка 10 мешков цемента»;
2) middleware возвращает `action=create_object` и набор `fields`;
3) расширение выполняет подготовку заполнения и, при необходимости, предлагает создать отсутствующие элементы (клиент/товар), после чего открывает форму нового документа.

Сценарий S‑04 «Создать канбан‑задачу»:
1) пользователь вводит «Добавь задачу: подготовить отчёт по продажам для Иванова до пятницы»;
2) middleware возвращает `action=create_kanban_task`, `data.title="Подготовить отчёт по продажам"`, `data.assignee="Иванов"`, `data.priority="medium"`;
3) расширение отправляет POST‑запрос `/kanban/tasks` в middleware и выводит карточку созданной задачи в чате.

Сценарий S‑05 «Показать канбан‑доску»:
1) пользователь нажимает быструю кнопку «📌 Канбан» или вводит «Покажи канбан доску»;
2) middleware определяет `action=show_kanban`;
3) расширение отправляет GET‑запрос `/kanban/tasks`, получает список задач и формирует HTML‑визуализацию канбан‑доски с колонками (К выполнению / В работе / На проверке / Готово) и отображает её в HTML‑поле формы.

2.6 Проектирование системы авторизации и ролевой модели

Для обеспечения безопасного доступа к функциям ассистента проектируется система авторизации на основе JWT (JSON Web Tokens). Модель включает:

Роли пользователей:
- **admin** — полный доступ: управление пользователями, всеми канбан‑задачами, просмотр аналитики;
- **manager** — расширенный доступ: задачи своего департамента, создание документов, аналитика;
- **employee** — базовый доступ: свои задачи, консультации, просмотр коллег своего департамента.

Структура данных авторизации:
- Пользователь (User): username, password_hash (bcrypt), full_name, role, department_id, is_active, avatar_color, created_at;
- Департамент (Department): id, name, head_user_id, parent_id, created_at; агрегируемые поля: head_name, parent_name, employee_count

Алгоритм авторизации:
1) пользователь отправляет POST `/auth/login` с username и password;
2) middleware проверяет учетные данные (bcrypt‑верификация), формирует JWT‑токен с полями sub (username), user_id, exp;
3) при каждом запросе к защищённому эндпоинту проверяется заголовок `X-Auth-Token` (выбран нестандартный заголовок вместо `Authorization: Bearer`, поскольку облачные прокси‑серверы могут перехватывать стандартный заголовок);
4) на основе роли пользователя middleware фильтрует доступные данные (например, менеджер видит только задачи своего департамента).

Хранение данных авторизации: SQLite (легковесная встроенная БД, не требующая отдельного сервера). При первом запуске автоматически создаются таблицы и заполняются демо‑данными (4 департамента, 6 пользователей).



2.7 Проектирование прикладного расширения «Подбор моделей БПЛА по тендерной заявке» для ООО «АТС Технологии» (Коптра)

Раздел описывает проектирование прикладного расширения, демонстрирующего переносимость предложенной архитектуры на нишевую задачу подбора готовых моделей БПЛА и сборки конфигураций из комплектующих по тендерной заявке (постановка задачи — раздел 1.5). Все архитектурные решения сохраняют совместимость с базовым ассистентом и используют его инфраструктуру: чат-форму, whitelist-протокол `action/data`, авторизацию JWT, RAG-слой и форму подбора, построенную в той же гибридной парадигме (таблицы формы + кнопки + опциональное HTML-поле).

2.7.1 Архитектура прикладного расширения

Прикладное расширение оформляется как отдельное расширение конфигурации УНФ (`1C_Drones_Extension.bsl`), независимое от расширения базового ассистента. Это решение принято по двум причинам:

- организации, не работающие с БПЛА, могут не подключать расширение, и ассистент будет функционировать как раньше;
- ядро ассистента можно развивать без необходимости тестировать его на каталоге продукции компании-производителя.

На уровне middleware независимость обеспечивается фича-флагом `DRONE_FEATURE_ENABLED` в файле окружения `.env`: при выключенном флаге эндпоинты `/tender/*` возвращают HTTP 404, а пост-обработка ключевых слов тендера в чате не активируется. Внутри прикладного расширения добавляются:

- два новых справочника в конфигурации УНФ: `Справочник.МоделиБПЛА` и `Справочник.Комплектующие`;
- четыре перечисления: `ТипыБПЛА`, `НазначенияБПЛА`, `КатегорииКомплектующих`, `ИсточникиКаталога`;
- одна обработка с управляемой формой: `Обработка.ПодборПоТендеру`;
- три новых действия в whitelist ассистента: `parse_tender` (извлечение требований), `match_drone` (подбор готовой модели), `build_config` (сборка конфигурации);
- четыре новых сервиса в middleware: `tender_service` (координатор), `drone_index_service` (изолированный векторный индекс по моделям), `component_index_service` (изолированный индекс по комплектующим), `config_builder` (детерминированный сборщик BoM);
- два новых HTTP-эндпоинта: `POST /tender/parse` и `POST /tender/match`.

Архитектурная схема прикладного расширения представлена ниже. Стрелки показывают, что модули, добавляемые расширением, опираются на существующие сервисы (LLMService, MetadataService, AuthService) и не модифицируют их.

2.7.2 Структуры данных тендера и каталога

Структура входного запроса в форме `TenderRequirements` фиксирует все поля, которые могут быть извлечены LLM из текста тендерной заявки. Pydantic-модель построена так, чтобы каждое поле было опциональным и снабжалось валидацией диапазона (например, количество моторов от 1 до 12, грузоподъёмность от 0 до 200 кг). Особое значение имеет поле `intent` — режим работы, который может принимать три значения:

- `ready_model` — пользователь хочет получить только готовую модель из каталога (типичный тендер на закупку дронов);
- `build_config` — пользователь хочет получить сборку из комплектующих (типичный тендер на закупку учебного набора, ремкомплекта или полётного контроллера с обвязкой);
- `auto` — режим определяется автоматически: запускаются оба алгоритма, в результат включаются и готовые модели, и сборка.

Поле `purpose` содержит назначение БПЛА (educational / fpv_racing / logistics / aerial_photo / surveillance / general) и используется для повышения веса соответствующих характеристик в скоринге: для образовательных целей повышается вес поддержки программирования (Python, Lua) и наличия учебной документации, для FPV-гонок — вес скоростных характеристик и веса самого аппарата, для логистики — грузоподъёмности и времени полёта.

Каталог моделей (`Справочник.МоделиБПЛА`) содержит 24 реквизита, которые делятся на пять групп:
- идентификаторы (Код, Артикул, Наименование, Производитель, СтранаПроизводства);
- классификационные (ТипКонструкции, Назначение, ИсточникКаталога — own/partner);
- ТТХ-числовые (КоличествоМоторов, ВзлётнаяМасса, Грузоподъёмность, ВремяПолёта, ДальностьСвязи, МаксимальнаяСкорость, ДиагональРамы);
- ТТХ-текстовые (РабочаяТемпература, СтепеньЗащиты, ПоддерживаемыеНагрузки, СовместимоеПО, ЯзыкПрограммирования);
- коммерческие и сервисные (ЦенаРозничная, СсылкаНаДокументацию, Описание, НеИспользуется).

Реквизит `ИсточникКаталога` позволяет различать собственные продукты Коптры (`own`) и партнёрские позиции (`partner`). Это разделение критично для алгоритма подбора: при равном скоринге собственные модели имеют приоритет, а в финальный score включается «бонус собственного бренда», вычисляемый как доля стоимости own-комплектующих в итоговой конфигурации.

Каталог комплектующих (`Справочник.Комплектующие`) использует более компактную схему с одним универсальным реквизитом `СовместимостьJSON`, в котором хранятся категорийно-зависимые параметры. Это решение принято для устранения «разрастания» справочника десятками реквизитов, релевантных только для одной-двух категорий. Состав параметров `СовместимостьJSON` фиксирован для каждой категории и реализуется в коде сервиса `config_builder` на стороне middleware:

- для рамы: количество посадочных мест моторов, размер посадочного места, максимальный диаметр пропеллера, диагональ;
- для полётного контроллера: модель MCU, поддерживаемые прошивки, диапазон входных напряжений, количество UART, поддерживаемые языки программирования;
- для ESC: непрерывный ток, пиковый ток, диапазон напряжений, поддерживаемые протоколы (DShot600, PWM), наличие BEC;
- для мотора: KV-рейтинг, размер статора, размер посадочного места, масса, максимальный ток, диапазон напряжений;
- для батареи: химия (LiPo / LiHV / Li-Ion), количество ячеек, ёмкость в мА·ч, C-рейтинг, масса, тип разъёма;
- для пропеллера: диаметр, шаг, количество лопастей, материал, диаметр посадочного отверстия.

Хранение совместимости в JSON-строке вместо набора отдельных реквизитов позволяет при необходимости расширить набор полей без изменений в метаданных конфигурации; форма элемента справочника содержит редактор JSON, который при выборе категории генерирует подходящий шаблон.

2.7.3 Алгоритм извлечения требований из текста тендера

Для преобразования произвольного текста тендера в структурированный объект `TenderRequirements` применяется однократный вызов LLM с детерминированными настройками: `temperature=0`, инструктивный системный промпт, фиксированная схема ответа. Промпт содержит:

1) описание роли модели (парсер тендерных требований к БПЛА);
2) полную схему ожидаемого JSON с типами полей и допустимыми значениями (включая enum-перечисления для `intent`, `drone_type`, `purpose`, `required_payloads`);
3) правила нормализации лексики (квадрокоптер→quadcopter, тепловизор→thermal_camera, программируемый→добавить «Python» в programmable_languages и т. п.);
4) три few-shot-примера на русском языке, демонстрирующих ожидаемый формат ответа на типичных тендерах (готовая модель, сборка, гибрид);
5) явное указание на формат вывода: «только JSON, без обёртки markdown».

Извлечение JSON из ответа модели выполняется тем же многоуровневым экстрактором, что и в базовом ассистенте (метод `_extract_json` сервиса `LLMService`): сначала ищется блок ```json ... ```, затем сбалансированные фигурные скобки, затем применяется санитизация (удаление комментариев, хвостовых запятых, замена одинарных кавычек). Если ни один кандидат не парсится — поднимается исключение `TenderParseError`, на форме «Подбор» отображается сообщение «Не удалось распознать требования. Попробуйте уточнить формулировку или ввести характеристики списком», и поля формы остаются доступными для ручного ввода.

Pydantic-валидация дополняет проверку JSON-совместимости проверкой диапазонов и кросс-валидацией (например, `motor_count_min ≤ motor_count_max`). Поле `confidence` (0..1) заполняется самой моделью на основе полноты извлечённых данных и используется на форме как индикатор: при `confidence < 0.5` пользователю показывается предупреждение «Распознавание неточное, проверьте поля».

2.7.4 Алгоритм подбора готовых моделей

Подбор готовых моделей в режимах `ready_model` и `auto` выполняется по двухэтапной схеме «retrieval → rerank», адаптированной под каталог компании-производителя.

**Этап 1: семантический поиск (retrieval).** Структурированные требования преобразуются в текстовый запрос путём конкатенации заполненных полей: тип конструкции, назначение, ключевые ТТХ, требуемые нагрузки, языки программирования. Для усиления вклада типа конструкции и назначения в результат поиска эти поля повторяются в строке запроса. Запрос векторизуется мультиязычной моделью `paraphrase-multilingual-MiniLM-L12-v2`, и по предвычисленным эмбеддингам справочника моделей вычисляется косинусное сходство:

   sim(q, m) = (v(q) · v(m)) / (||v(q)|| · ||v(m)||)

Возвращаются top‑K (по умолчанию K=10) моделей. К результату дополнительно применяются:
- жёсткий фильтр по `drone_type`: оставляются только модели запрошенного типа; если после фильтра остаётся меньше трёх кандидатов — фильтр отключается и поиск выполняется по всему каталогу;
- мягкий фильтр по бюджету: модели, цена которых ≤ 1,2× указанного бюджета, получают надбавку +0,05 к косинусному score; остальные не отсекаются, но помечаются `out_of_budget=true`.

**Этап 2: LLM-реранжирование (rerank).** Top‑K кандидатов передаются в LLM в виде табличного описания (модель, ТТХ, источник каталога, цена). Модель получает требования и инструкцию вернуть JSON со списком ранжированных моделей и обоснованием. Для каждого кандидата модель должна заполнить:
- `score` — оценка от 0 до 100;
- `matches` — массив выполненных требований («поддерживает Python», «время полёта 25 минут ≥ 20 требуемых»);
- `gaps` — массив расхождений («дальность 0,3 км < 1 км требуемой»);
- `explanation` — текстовое обоснование длиной до 280 символов на русском языке.

Возвращённый ranking фильтруется на стороне middleware: модели, чьи `model_id` отсутствовали в списке кандидатов, удаляются — это защита от «галлюцинаций» LLM, способной выдумать несуществующее наименование. При отсутствии валидного JSON или пустом ranking применяется fallback: используется ranking по косинусному score из этапа 1, флаг `fallback_used=true`, в `summary` помечается «LLM-rerank недоступен».

**Финальный взвешенный скоринг.** Финальная оценка каждой модели вычисляется как взвешенная сумма трёх компонент:

   final_score = 100 × (W_COSINE × cosine + W_COVER × coverage + W_LLM × (llm_score/100))

где:
- `cosine` — нормализованное косинусное сходство (0..1) с этапа 1;
- `coverage` — доля выполненных требований, рассчитываемая детерминированно на стороне Python (без участия LLM): по каждому числовому требованию проверяется попадание характеристики модели в диапазон, по каждому категориальному — точное совпадение или вхождение в список;
- `llm_score` — оценка LLM (0..100) с этапа 2, нормализованная до 0..1.

Веса по умолчанию: `W_COSINE=0,20`, `W_COVER=0,35`, `W_LLM=0,45`. Сумма равна единице. Веса вынесены в переменные окружения, что позволяет в главе 3 диплома сравнивать четыре стратегии скоринга (`only_cosine`, `only_coverage`, `only_llm`, `hybrid`) и эмпирически обосновать выбор гибридной стратегии.

Введение `coverage` как отдельной компоненты, не зависящей от LLM, обеспечивает «нижнюю границу» качества при отказе LLM-rerank: даже в полностью fallback-режиме у пользователя остаётся осмысленный rule-based ranking. Это свойство проверяется отдельным unit-тестом и важно для надёжности производственного использования.

2.7.5 Алгоритм сборки конфигурации из комплектующих

Сборка конфигурации в режимах `build_config` и `auto` выполняется детерминированным алгоритмом `ConfigBuilder.build(requirements)`. Использование детерминированного алгоритма вместо LLM на этом этапе принципиально: речь идёт о физических ограничениях (посадочные размеры, диапазоны напряжений, токи с запасом), которые требуют точной арифметики, и любая ошибка LLM здесь приведёт к «нерабочей» конфигурации. LLM привлекается только на финальной стадии для формирования текстового обоснования собранной BoM.

Алгоритм состоит из пяти последовательных этапов, каждый из которых сужает множество допустимых компонентов с учётом ограничений предыдущих:

**Этап 1: выбор рамы.** Из каталога комплектующих категории `frame` выбираются позиции, у которых:
- `motor_mount_count` совпадает с требуемым количеством моторов (или с `motor_count_min` при отсутствии явного количества);
- `prop_size_inch_max` ≥ требуемого размера пропеллера (если задан) или ≥ значения по умолчанию для назначения (5″ для FPV, 7–10″ для логистики, 5–7″ для образования);
- `diagonal_mm` соответствует требованию `frame_diagonal_mm` (если задано).

При наличии нескольких кандидатов применяется правило приоритета: рамы с `catalog_source="own"` (собственная разработка Коптры) получают предпочтение даже при сопоставимых характеристиках.

**Этап 2: выбор полётного контроллера.** Из категории `flight_controller` выбираются позиции, у которых:
- поддерживается требуемый язык программирования (для образовательных тендеров обычно Python);
- диапазон входных напряжений `voltage_input_v` пересекается с напряжением целевой батареи (из требований или по умолчанию 4S=14,8 В для FPV, 3S=11,1 В для учебных дронов);
- количество UART достаточно для подключения требуемой периферии (GPS, видеосистема).

Для каталога Коптры по умолчанию выбирается «Коптра ИПК1» (STM32F405, поддержка Python, 5 UART), что соответствует приоритету собственного бренда.

**Этап 3: выбор моторов.** Из категории `motor` подбирается комплект из N моторов (по `motor_mount_count` рамы), удовлетворяющий ограничениям:
- `mount_size_mm` совпадает с посадочным размером рамы;
- диапазон напряжений `voltage_v` пересекается с диапазоном батареи;
- KV-рейтинг согласован с диаметром пропеллера по таблице соответствия (заложенной в коде `config_builder`): для пропеллеров 5″ предпочтительный KV — 2200–2400, для 7″ — 1700–1900, для 10″ — 600–900.

**Этап 4: выбор ESC.** Из категории `esc` выбирается N регуляторов с условиями:
- непрерывный ток `current_continuous_a` ≥ максимального тока мотора с запасом не менее 20% (правило, заложенное в `_compat_motor_esc`);
- диапазон напряжений `voltage_v` включает напряжение батареи;
- поддерживаются совместимые с контроллером протоколы (например, DShot600 для современных полётных контроллеров).

**Этап 5: выбор батареи и пропеллеров.** Из категорий `battery` и `propeller` подбираются совместимые позиции:
- ёмкость батареи рассчитывается из требуемого времени полёта по формуле:

      flight_time_min ≈ capacity_mAh × discharge × 60 / (current_draw_a × 1000)

где `discharge` — допустимая глубина разряда (обычно 0,8 для LiPo), `current_draw_a` — суммарный ток моторов в крейсерском режиме (≈ 30–40% от максимального);
- пропеллеры выбираются по согласованию с KV мотора и `prop_size_inch_max` рамы; их диаметр не должен превышать предельный для рамы.

**Скоринг BoM.** Финальная оценка собранной конфигурации:

   bom_score = 100 × (BOM_W_COVER × coverage + BOM_W_COMPAT × compat + BOM_W_OWN × own_share + BOM_W_PRICE_FIT × price_fit)

где:
- `coverage` — доля закрытых обязательных категорий BoM (рама, контроллер, моторы, ESC, батарея, пропеллеры);
- `compat` — доля проверок совместимости, прошедших без warnings;
- `own_share` — доля стоимости комплектующих собственной разработки в итоговой конфигурации;
- `price_fit` — приближение к бюджету (1, если в пределах бюджета; пропорциональное снижение при превышении).

Веса: `BOM_W_COVER=0,35`, `BOM_W_COMPAT=0,30`, `BOM_W_OWN=0,15`, `BOM_W_PRICE_FIT=0,20`.

Если на каком-либо этапе ни один компонент в каталоге не удовлетворяет ограничениям, алгоритм не прерывается, а добавляет запись в `BoMResult.compatibility_warnings` («Нет совместимой батареи на 4S с током ≥ 80 А»), помечает `is_complete=false` и продолжает сборку, насколько возможно. Менеджеру возвращается частичная конфигурация с указанием, какие звенья отсутствуют, чтобы он мог либо отказаться от участия в тендере, либо инициировать закупку у партнёра.

2.7.6 Проектирование пользовательского интерфейса формы «Подбор по тендеру»

Форма «Подбор по тендеру» проектируется как обработка с управляемой формой и тремя вкладками. Гибридный принцип, заложенный в базовом ассистенте (раздел 2.5), сохраняется: основные данные отображаются стандартными элементами формы (таблицы, поля ввода, кнопки), что обеспечивает совместимость с мобильным клиентом «1С:Предприятие»; HTML-поле используется опционально для визуальных диаграмм сборки.

**Вкладка 1 «Текст и требования».** Содержит:
- многострочное поле ввода `ТекстТендера` для вставки текста заявки;
- кнопку «Распознать требования», вызывающую `POST /tender/parse`;
- таблицу из двух колонок «Поле — Значение», в которой отображаются распознанные требования с возможностью ручного редактирования (типичный сценарий: LLM не распозналa бюджет, менеджер вписывает его вручную);
- переключатель режима подбора (`intent`: «Готовая модель» / «Сборка из комплектующих» / «Авто»);
- кнопку «Подобрать», вызывающую `POST /tender/match` с текущим состоянием требований и режимом.

**Вкладка 2 «Готовые модели».** Содержит таблицу результатов с колонками:
- «Модель» (наименование);
- «Источник» (own / partner с цветовой индикацией: синий значок для собственных, серый — для партнёрских);
- «Скор» (числовое значение 0..100 с цветовой шкалой: зелёный для score ≥ 80, жёлтый 60..79, серый <60);
- «Цена» с пометкой «вне бюджета» при `out_of_budget=true`;
- «Соответствия» (мультистрока с маркерами выполненных требований);
- «Расхождения» (мультистрока с маркерами невыполненных или частично выполненных);
- «Действия» (кнопки в строке: «Открыть карточку», «Создать заказ», «Сохранить как задачу», флажок «В сравнение»).

Под таблицей размещаются кнопки «Сравнить выбранные» (открывает форму сравнения «требование ↔ модель 1 ↔ модель 2 ↔ ...» с зелёной/оранжевой подсветкой ячеек), «Экспорт КП в CSV».

**Вкладка 3 «Сборка конфигурации».** Содержит:
- табличную часть BoM с колонками «Категория», «Компонент», «Источник», «Кол-во», «Цена за единицу», «Сумма», «Примечания совместимости»;
- блок итоговых метрик: общая стоимость, расчётная масса, прогнозируемое время полёта, доля собственного бренда (own_brand_share);
- блок предупреждений совместимости (`compatibility_warnings`) с указанием конкретных ограничений (например, «Батарея на пределе тока ESC: 80 А ≈ предельные 80 А»);
- кнопки «Создать заказ из BoM», «Экспорт BoM в CSV», «Сравнить с готовыми моделями».

Условное оформление таблиц задаётся программно через `ЭлементОтбораКомпоновкиДанных` (тот же подход, что и в базовом ассистенте) для гарантированной корректной отрисовки в мобильном клиенте.

2.7.7 Сценарии использования прикладного расширения

Сценарий S‑D‑01 «Подбор готовой модели по тендеру в чате»:
1) пользователь вставляет в чат-форму ассистента текст тендера: «Требуется учебный программируемый квадрокоптер с поддержкой Python, время полёта не менее 15 минут, рама 300 мм, для уроков информатики в школе. Количество — 30 шт., бюджет 60 тыс. руб. за единицу»;
2) middleware распознаёт маркеры тендера, post-processing-блок переписывает action на `parse_tender`, в `data` помещается оригинальный текст;
3) расширение 1С открывает форму «Подбор по тендеру», передаёт текст и автоматически вызывает `POST /tender/parse`;
4) распознанные требования заполняются на вкладке 1, менеджер видит `intent="ready_model"`, `purpose="educational"`, `programmable_languages=["Python"]`, `flight_time_min_minutes=15`, `frame_diagonal_mm=300`, `quantity=30`, `budget_per_unit_rub=60000`;
5) менеджер нажимает «Подобрать», система запускает retrieval+rerank;
6) на вкладке 2 выводится «Коптра Орлёнок» (score 92, source=own), «Pioneer Mini» (score 78, source=partner), «ELI Trainer» (score 71, source=partner);
7) менеджер открывает карточку «Коптра Орлёнок», нажимает «Создать заказ», цепочка `Шаг1_ПроверкаКлиента..Шаг3_Финал` подготавливает заказ с количеством 30 единиц.

Сценарий S‑D‑02 «Сборка комплекта для самостоятельной сборки»:
1) пользователь открывает форму «Подбор по тендеру» через быструю кнопку и вставляет текст: «Нужен набор комплектующих для FPV-дрона: рама 220 мм, полётный контроллер с поддержкой Betaflight, 4 мотора 2400 KV, ESC 60 А, батарея 4S 1500 мА·ч, пропеллеры 5 дюймов»;
2) менеджер нажимает «Распознать требования», система получает `intent="build_config"`, `frame_diagonal_mm=220`, `propeller_size_inch=5`, `compatible_software=["Betaflight"]` и т. д.;
3) менеджер нажимает «Подобрать», ConfigBuilder запускается напрямую (готовые модели не ищутся при `intent="build_config"`);
4) на вкладке 3 выводится BoM: «Рама Коптра 220 мм» (own), «Коптра ИПК1» (own), «Мотор Коптра 2207 2400KV ×4» (own), «Коптра ESC 60A ×4» (own), «Батарея Tattu 4S 1500mAh» (partner), «Пропеллеры HQProp 5″ ×8» (partner);
5) `own_brand_share = 0,72`, общая стоимость и расчётное время полёта выводятся в итоговом блоке;
6) менеджер нажимает «Создать заказ из BoM», система открывает заказ покупателя с шестью строками табличной части.

Сценарий S‑D‑03 «Авто-режим: тендер допускает оба варианта»:
1) пользователь вставляет тендер: «Поставка комплекта оборудования для лаборатории беспилотных систем: квадрокоптер программируемый или комплект для самостоятельной сборки на 4 моторах, для 1 курса магистратуры»;
2) при `intent="auto"` запускаются оба алгоритма;
3) на вкладке 2 выводятся «Коптра Орлёнок» и «Коптра Орлёнок Расширенный набор»;
4) на вкладке 3 выводится BoM на базе ИПК1 с тренировочной рамой 300 мм;
5) менеджер сравнивает оба варианта по итоговой цене и выбирает один из них.

Эти сценарии демонстрируют, что прикладное расширение работает в трёх типичных режимах работы менеджера по тендерам ООО «АТС Технологии»: явная закупка готовой модели, явная закупка комплекта для сборки, неоднозначный тендер с возможностью предложения обоих вариантов. Архитектура ассистента позволяет обрабатывать все три случая одним и тем же интерфейсом без переключения пользователем сложных режимов работы.
