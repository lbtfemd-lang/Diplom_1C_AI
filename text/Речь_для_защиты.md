### [Слайд 3] Проблемы пользователей 1С:УНФ
**Докладчик:**  
Анализ предметной области проводился на базе торгового предприятия ООО «ЛюксонДекор» с месячным документооборотом свыше 3000 документов. Были выявлены следующие барьеры:
- **Интерфейсная перегрузка**: типовая конфигурация содержит более 200 форм, поиск нужного отчета занимает до 5 минут.
- **Терминологический разрыв**: пользователи вводят неформальные запросы («накладная», «платежка», «долги»), в то время как 1С требует точного знания названий объектов («Реализация товаров и услуг», «Поступление на счет»).
- **Ошибки ввода данных**: 25% обращений в поддержку вызваны некорректным заполнением обязательных реквизитов.
- **Потеря поручений**: отсутствие единого инструмента контроля задач сотрудников внутри 1С ведет к срыву сроков.

### [Слайд 4] Обзор аналогов
**Докладчик:**  
Изучение рынка показало, что существующие решения обладают ограничениями. Встроенный чат-бот «Ася» работает по жестким шаблонам и не интегрируется с УНФ. Прямое подключение внешних LLM, таких как GigaChat, через стандартные API страдает от «галлюцинаций» (модель не знает реальной структуры базы данных). Платные коннекторы создают зависимость от вендора. 

Было принято решение разработать собственную клиент-серверную систему на базе расширения 1С и FastAPI-middleware с использованием локальной векторной базы данных для RAG.

### [Слайд 5] Требования к системе
**Докладчик:**  
К разработке были предъявлены строгие требования. Функциональные включают: обработку запросов на русском языке, поиск документов, подготовку черновиков документов, проверку складских остатков и задолженностей, а также управление задачами. 

Среди нефункциональных требований ключевыми являются: время ответа системы менее 3 секунд на команду, точность понимания намерений выше 90%, интеграция без изменения типовой конфигурации (через механизм расширений) и многоуровневая безопасность данных.

### [Слайд 7] Пользовательские сценарии
**Докладчик:**  
Разработанный ассистент поддерживает широкий спектр сценариев:
- **Навигация**: по запросу «Покажи реализации за сентябрь» ассистент открывает список документов с установленным фильтром.
- **Аналитика**: по запросу «Какие заказы в работе?» формируется сводная информация.
- **Поиск**: поиск документов по неполным реквизитам.
- **Запросы показателей**: мгновенная проверка остатков номенклатуры и задолженностей контрагентов непосредственно через чат.

### [Слайд 8] Сценарий создания документа
**Докладчик:**  
Особое внимание уделено сценарию создания документов. Пользователь формулирует запрос в свободной форме: «Создай реализацию ООО Ромашка, 10 штук товара А». 

Ассистент извлекает сущности, проверяет наличие контрагента и товара в справочниках 1С (при их отсутствии предлагает создать их через нативные формы). Затем система генерирует предзаполненный черновик документа в 1С. **Важно**: запись и проведение документа осуществляются только после визуальной проверки и подтверждения действия человеком, что исключает порчу данных.

### [Слайд 9] Архитектура решения
**Докладчик:**  
На слайде представлена архитектура системы. Клиентская часть (расширение 1С) содержит HTML-поле чата, диспетчер команд и HTTP-клиент. Она взаимодействует с FastAPI middleware по защищенному протоколу REST API с использованием JSON. 

Middleware выполняет маршрутизацию, семантический поиск, авторизацию пользователей по токенам JWT с ролевой моделью (`admin`, `manager`, `employee`) и обращается к векторной базе данных и LLM API.

---

### [Слайд 10] Алгоритм обработки запроса
**Докладчик:**  
Процесс обработки запроса разделен на 6 этапов:
1. Пользователь вводит текст в чат.
2. LLM на стороне сервера определяет намерение (`intent`) и вычленяет параметры.
3. RAG-механизм сопоставляет термины с реальными метаданными базы 1С.
4. Генерируется структурированная команда (в формате `action`/`data`).
5. На стороне 1С выполняется валидация прав доступа и корректность реквизитов.
6. Выводится ответ в чат и выполняется действие (например, открытие формы).

### [Слайд 11] RAG по метаданным 1С
**Докладчик:**  
Главным вызовом при интеграции ИИ в 1С является терминологический барьер. Спроектированный нами RAG-модуль решает проблему галлюцинаций модели. При выгрузке метаданных строится векторный индекс. 

Когда пользователь пишет «продажа», RAG находит соответствие с `РеализацияТоваровУслуг`, а «клиент» переводится в `Справочник.Контрагенты`. В результате точность формирования команд для LLM повысилась с 60% до 95%.

---

### [Слайд 12] Безопасность
**Докладчик:**  
Безопасность системы реализована по многоуровневой схеме. Языковая модель не имеет прямого доступа к базе данных 1С — обмен идет через жестко контролируемый API. 

Выполнение любых команд ограничено белым списком безопасных операций чтения. Модель способна создавать только черновики документов без проведения, а ролевая модель JWT-авторизации гарантирует, что менеджер или складской сотрудник увидит только разрешенную информацию.

### [Слайд 13] Интерфейс пользователя и Канбан-доска
**Докладчик:**  
Интерфейс ассистента интегрирован непосредственно в рабочее пространство 1С. Он выполнен в виде нативной чат-панели с кнопками быстрых действий. 

Также нами спроектирована и внедрена канбан-доска для управления задачами. Она разработана с учетом кроссплатформенности: для настольных компьютеров используется интерактивный HTML-интерфейс, а для мобильных устройств реализована нативная форма 1С, стабильно работающая в мобильном клиенте платформы.
